# воспроизведение EntroGuard

Практический проект: реализация и эксперименты по методу **EntroGuard** —
защите эмбеддингов текста от **Embedding Inversion Attack (EIA)** через
максимизацию энтропии промежуточных ("logit-lens") распределений
атакующей модели, с последующим ограничением величины возмущения
алгоритмом **Bound-aware Perturbation Adaptation**.

Часть кода (`models.py`, `entroguard.py`, `data.py`, `metrics.py`) содержит прямые ссылки на формулы
статьи (eq. 5, 8, 9, 10) и Algorithm 1 в докстрингах/комментариях. Точных
библиографических данных статьи в репозитории нет, поэтому ниже она
называется просто "статья" / "EntroGuard" — переносился метод, а не
цитата из конкретного PDF.

## Идея эксперимента

1. **Эксперимент 1** — воспроизвести архитектуру, близкую к описанной в
   статье, и сравнить эффективность EntroGuard с базовыми защитами
   (без защиты, гауссов шум, PGD) против одного и того же
   transformer-атакующего, при одинаковом бюджете возмущения (epsilon).
2. **Эксперимент 2** — проверить, насколько защита, обученная под
   transformer-атакующего, переносится на принципиально другую,
   **нетрансформерную** архитектуру атакующего (LSTM decoder), и
   сравнить это с защитой, обученной сразу под LSTM ("adaptive").

По умолчанию (`config.DATA_SOURCE = "personachat"`) используются
реальные данные — PersonaChat и MS MARCO, см. раздел "Данные" ниже.
Есть и офлайн-фолбэк: синтетический шаблонный корпус
(`config.DATA_SOURCE = "synthetic"`), специально сделанный достаточно
регулярным, чтобы атакующая модель могла реально научиться
инвертировать эмбеддинги без сети — полезно для быстрой проверки, что
пайплайн не сломан (см. докстринг `data.py`).

## Что здесь понимается под "эффективностью"

Три независимые оси, по которым сравниваются защиты — таблицы и график
в `results/` содержат все три:

| Ось | Метрика | Где считается |
|---|---|---|
| **Приватность** (ниже = лучше) | BLEU-2, ROUGE-1, EMR между текстом, восстановленным атакующим, и оригиналом | `metrics.privacy_leakage_report` |
| **Полезность** (выше = лучше) | Recall@k пересечения top-k выдачи retrieval для защищённого и чистого запроса | `metrics.retrieval_recall_overlap`, eq.(5) |
| **Эффективность/скорость** (ниже = лучше) | мс на 1000 запросов на применение защиты | `evaluate_defense.run_defense` (`utils.Timer`) |

Третья ось — намеренное дополнение: EntroGuard — это один forward-pass
через обученный генератор, а PGD-защита — это `n_steps` шагов
градиентной оптимизации с доступом к весам атакующего (white-box).
Разница в скорости — часть практического сравнения, а не просто
приватность/полезность.

## Структура проекта

```
data.py                — синтетический корпус + загрузчики PersonaChat/MS MARCO + Vocab
download_data.py         — скачивает и кэширует PersonaChat/MS MARCO (шаг 0)
models.py               — EmbeddingModel (frozen victim), TransformerAttacker,
                           LSTMAttacker (нетрансформерный атакующий),
                           PerturbationGenerator (G_theta, DenseNet-MLP)
entroguard.py            — лоссы (eq. 8-10), Algorithm 1 (bound_aware_adaptation),
                           базовые защиты (gaussian_noise_defense, pgd_defense)
metrics.py               — BLEU-2/ROUGE-1/EMR, retrieval_recall_overlap (eq. 5)
config.py                — все гиперпараметры, источник данных и пути (переопределяемы через ENTRO_* env)
utils.py                 — seed, разбиение данных, батчи, чекпоинты, таймер
train_attacker.py         — предобучение атакующего (--arch transformer|lstm), пишет history_*.json
train_entroguard.py       — обучение G_theta против выбранного атакующего (--target), пишет history_*.json
evaluate_defense.py       — Эксперимент 1: none / gaussian / pgd / entroguard vs transformer
evaluate_transfer.py      — Эксперимент 2: те же защиты + zero-shot/adaptive entroguard vs LSTM
run_all.py                — прогоняет весь пайплайн одной командой (чистый CLI, без интерфейса)
viz_svg.py                — SVG-графики без внешних зависимостей (line/grouped-bar chart)
make_report.py            — собирает results/*.json в один HTML-отчёт (report.html)
app.py                    — веб-панель: запуск шагов из браузера, живые логи, результаты
checkpoints/              — веса моделей (создаётся автоматически, в .gitignore)
results/                  — json/markdown/png/html с результатами (создаётся автоматически)
runs/                     — логи задач, запущенных через app.py (создаётся автоматически)
```

## Интерфейс (веб-панель)

```bash
python app.py            # затем открыть http://localhost:8000
```

Локальный дашборд (stdlib `http.server`, без новых зависимостей —
работает офлайн, отдельного фронтенд-стека нет):

- **Вкладка "Пайплайн"** — карточка на каждый шаг (скачать данные →
  обучить attacker'ов → обучить EntroGuard → оба эксперимента), кнопка
  "Запустить", живой лог (полностью тот же вывод, что и в терминале,
  подтягивается раз в ~1.2с), статус (не запущено / выполняется /
  готово / ошибка с кодом возврата). Рядом с шагами, у которых есть
  предпосылки, показано, какие чекпоинты уже существуют
  (`✓`/`✗`) — например, `train_entroguard.py --target lstm` требует
  `attacker_lstm.pt`.
- **Настройки запуска** над карточками — источник данных
  (`personachat`/`synthetic`) и основные гиперпараметры (эпохи,
  epsilon, alpha/beta/gamma); применяются к следующему запуску через
  `ENTRO_*` переменные окружения (см. `config.py`), без правки файлов.
  Можно, например, запустить `evaluate_defense.py` на `synthetic` для
  быстрой проверки, а обучение — на `personachat`.
- **Вкладка "Результаты"** — тот же отчёт, что генерирует
  `make_report.py`: кривые обучения по эпохам (`results/history_*.json`)
  и сравнение защит в Экспериментах 1/2 (графики + таблицы +
  автовыводы). Обновляется по кнопке или сразу после завершения любого
  шага.

Процессы — обычные `subprocess.Popen` на этой же машине (используют
CUDA автоматически, как и при запуске из терминала); закрытие вкладки
браузера их не останавливает, только остановка `app.py` (Ctrl+C) или
кнопка "Остановить" у конкретного шага. Один и тот же шаг нельзя
запустить второй раз, пока предыдущий не завершился; разные шаги можно
запускать параллельно, но на одной GPU это, как правило, только
замедлит оба.

Без сервера тот же отчёт можно получить статическим файлом:

```bash
python make_report.py    # -> results/report.html, открыть в браузере
```

## Данные

Две роли, две разные причины использовать разные корпуса — ровно как в
самой статье:

| Корпус | Роль | Что делает |
|---|---|---|
| **PersonaChat** | приватность / инверсия | короткие фразы о личных фактах ("i work as a nurse", "i have two cats") — на них учится и оценивается атакующий и EntroGuard (train/val/test split) |
| **MS MARCO** | полезность / retrieval | queries — что защищается и embedding-ится как поисковый запрос; passages — база документов для `retrieval_recall_overlap` (eq. 5). В обучении атакующего/EntroGuard НЕ участвует |

Источник данных переключается в `config.py`:

```python
DATA_SOURCE = "personachat"   # реальные корпуса (по умолчанию)
DATA_SOURCE = "synthetic"     # офлайн-фолбэк без сети, см. выше
```

Загрузка идёт через Hugging Face `datasets`:
- PersonaChat: `AlekseyKorshuk/persona-chat`, поле `personality` (по 4-5
  фраз о персоне на диалог) — `config.PERSONACHAT_MAX_SENTENCES`
  ограничивает итоговый размер корпуса.
- MS MARCO: `microsoft/ms_marco` / `v1.1`, поля `query` и `passages.passage_text`
  — `config.MSMARCO_MAX_QUERIES` / `MSMARCO_MAX_PASSAGES` ограничивают
  сколько запросов и уникальных пассажей взять (полный корпус MS MARCO
  — это ~8.8M пассажей, качать целиком не нужно).

Скачать/закэшировать оба корпуса заранее (нужна сеть один раз, дальше
`datasets` работает из локального кэша `~/.cache/huggingface`):

```bash
python download_data.py
```

Если структура датасета на HF hub окажется не такой, как ожидает
`data.load_personachat`/`data.load_msmarco` (названия колонок могут
меняться между версиями/ревизиями) — скрипт упадёт с понятным
`ValueError`, который печатает реальные `column_names` датасета; в этом
случае поправьте соответствующий загрузчик в `data.py` под фактическую
схему.

**Общий словарь.** `EmbeddingModel` и оба атакующих используют ОДИН
`Vocab`, построенный из объединения PersonaChat + MS MARCO
(`utils.load_dataset()`) — иначе слова MS MARCO не входили бы в словарь
и запросы/пассажи превращались бы в почти сплошной `<unk>` при подаче в
тот же embedding-энкодер. Словарь ограничен `config.VOCAB_MAX_SIZE`
(=20000) самыми частыми словами; редкие слова уходят в `<unk>`.
`utils.load_dataset()` и `utils.load_retrieval_pool()` вызывают одни и
те же функции загрузки с одними и теми же параметрами в каждом
скрипте/процессе — при стабильной ревизии датасета на HF hub это даёт
детерминированно одинаковый словарь везде без необходимости сохранять
его на диск.

## Установка

Проект использует `uv` (уже виден `uv.lock`), но подойдёт и обычный `pip`.

```bash
uv sync
```

или

```bash
pip install -e .
```

Зависимости: `torch`, `numpy`, `datasets` (загрузка PersonaChat/MS MARCO
с HF hub), `matplotlib` (график опционален — если модуль не установлен,
скрипты просто пропустят его и выведут предупреждение). Если остаётесь
на `config.DATA_SOURCE = "synthetic"`, `datasets` не нужен вообще —
импортируется он лениво, только внутри загрузчиков реальных корпусов.

### CUDA

Все модули (`config.py`, `models.py`, `metrics.py`, `entroguard.py`)
уже выбирают устройство так:

```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
```

Проверить, что PyTorch видит GPU, перед запуском:

```bash
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

Если `torch` установлен в CPU-варианте (как было в исходном
`.venv` на момент разработки — `2.14.0+cpu`), нужно поставить
CUDA-сборку под свою версию CUDA с pytorch.org, иначе всё отработает,
но на CPU.

Модели здесь намеренно компактные (учебный масштаб, ~100-200k
параметров) — это сделано, чтобы эксперимент воспроизводился быстро и
был читаем как код, а не для попытки побить SOTA. На GPU выигрыш в
скорости будет заметен прежде всего на батчах и в PGD-защите
(итеративная оптимизация), а не на переборе всего пайплайна.

## Порядок запуска

Через веб-панель (см. раздел "Интерфейс" ниже) — запускать шаги по
одному кнопками, видеть логи и результаты не выходя из браузера:

```bash
python app.py
```

Или из терминала, всё сразу:

```bash
python run_all.py
```

Или по шагам (так удобнее смотреть на промежуточный лог обучения):

```bash
# 0. Скачать и закэшировать PersonaChat + MS MARCO (один раз, нужна сеть)
python download_data.py

# 1. Предобучить атакующих на ЧИСТЫХ эмбеддингах (без защиты)
python train_attacker.py --arch transformer
python train_attacker.py --arch lstm

# 2. Обучить EntroGuard (генератор возмущений) против каждого атакующего
python train_entroguard.py --target transformer
python train_entroguard.py --target lstm

# 3. Эксперимент 1: сравнение защит против transformer-атакующего
python evaluate_defense.py

# 4. Эксперимент 2: перенос на LSTM-атакующего (zero-shot + adaptive)
python evaluate_transfer.py
```

Шаг 0 не обязателен — `datasets` сам скачает корпуса при первом
обращении из любого скрипта — но отдельно его удобно запустить, чтобы
сразу увидеть проблему с сетью/схемой датасета, не потратив время на
эпохи обучения впустую. `run_all.py` шаг 0 не включает (не должен
требовать сеть при повторных запусках после первого).

Чекпоинты сохраняются в `checkpoints/attacker_{arch}.pt` и
`checkpoints/entroguard_{target}.pt` — оценочные скрипты их читают,
переобучать заново каждый раз не нужно.

## Sequence length bookkeeping

Стоит проговорить явно, так как это единственное место, где легко
запутаться:

- `EmbeddingModel` кодирует предложение длиной `config.MAX_LEN` (=24) —
  из него получается фиксированный вектор `e0`. Реальные предложения
  длиннее (особенно MS MARCO passages) просто обрезаются по `MAX_LEN`
  токенов (`Vocab.encode` делает `ids[:max_len]`) — для пассажей это ок,
  они нужны только как элементы retrieval-базы, а не для декодирования.
- Атакующие (`TransformerAttacker`/`LSTMAttacker`) обучаются teacher-forcing
  на полной последовательности `[BOS, w1..wn, EOS, PAD...]` длиной
  `config.ATTACKER_SEQ_LEN = MAX_LEN + 1` (=25): `input_ids = full[:, :-1]`,
  `target_ids = full[:, 1:]` — обычный сдвиг на 1 токен для
  предсказания следующего токена.

Оба атакующих используют один и тот же `Vocab` (см. "Данные" выше про
общий словарь PersonaChat+MS MARCO), построенный детерминированно в
`utils.load_dataset()`, так что во всех скриптах индексы токенов
совпадают — включая MS MARCO queries/passages, приходящие отдельно
через `utils.load_retrieval_pool()`.

## Что смотреть в результатах

`evaluate_defense.py` пишет `results/exp1_table.md` и
`results/exp1_metrics.json`. Ожидаемая логика (если метод работает,
как описано в статье):

- `none` — максимальная утечка (BLEU-2/ROUGE-1 самые высокие), recall@k = 1.0 (эталон полезности).
- `gaussian` — просаживает приватность слабее всего при том же epsilon (случайный шум — самая "тупая" защита).
- `pgd` — сильнее всего давит на приватность (white-box, знает градиенты атакующего), но требует `n_steps` шагов оптимизации на каждый запрос — это должно быть видно в `ms_per_1k_queries`.
- `entroguard` — должен приближаться к `pgd` по приватности, оставаясь на порядок быстрее (один forward pass), и в идеале меньше проседать по `retrieval_recall@k`, чем `pgd`/`gaussian`, за счёт того, что обучен явно с `similarity_loss` (eq. 9) как частью цели.
- `EMR` (exact match) почти всегда будет `0.0000`, даже у `none` — это ожидаемо, метрика требует побуквенно точного совпадения всей фразы; на реальном тексте PersonaChat/MS MARCO ориентируйтесь на BLEU-2/ROUGE-1, а не на EMR.

**Известный баг, который был и теперь исправлен: коллапс генератора
EntroGuard.** На первом реальном прогоне (PersonaChat + MS MARCO)
`entroguard` давал BLEU-2≈0 и `retrieval_recall@5≈0.003` — на порядок
хуже `gaussian`/`pgd` по полезности при том же `epsilon`, что не
объяснялось "недообученностью". Диагностика (см. `git log`/историю
диалога) показала: обученный генератор выдавал **один и тот же вектор
огромной нормы независимо от входа** (норма выхода ~4650 против ~2 у
`e0`, попарное косинусное сходство между разными защищёнными
эмбеддингами ≈1.0000) — классический mode collapse. Причина —
`similarity_loss` (eq. 9) считается через косинусное сходство, которое
**инвариантно к масштабу**: ничто в лоссе `alpha*L_sim - beta*L_entropy
- gamma*L_CE` не штрафовало за огромную норму `e_prime`, и оптимизатор
этим воспользовался, найдя вырожденное решение, которое дёшево
проходит по `sim_loss` и попутно обнуляет CE/увеличивает энтропию
атакующего — не за счёт умной защиты, а за счёт полного уничтожения
информации на входе. Из-за этого `bound_aware_adaptation` (Algorithm 1,
рассчитанный на "разумные" по масштабу возмущения) не успевал спроецировать
результат обратно в `epsilon`-шар за отведённые итерации — реальное
косинусное расстояние оставалось ≈0.44 вместо заявленных 0.15, то есть
`entroguard` в таблицах фактически работал с втрое большим бюджетом,
чем остальные защиты.

Фикс — `entroguard.rescale_to_e0_norm(e0, e_prime)`, которая
перенормирует сырой выход генератора к `‖e0‖` **до** того, как его
увидит любой лосс (используется и в обучении, и в `evaluate()`, и в
`run_defense`). Так cosine-based `similarity_loss` больше нельзя
"обмануть" масштабом — генератору приходится соревноваться только
направлением, как и задумано в eq. (9)-(10). Проверено на реальных
данных (офлайн, 4 эпохи для быстрой проверки): норма выхода теперь
равна норме `e0`, `bound_aware_adaptation` укладывается в `epsilon`
(0.135-0.145 вместо 0.44), попарное сходство между разными защищёнными
эмбеддингами упало с 1.0000 до ~0.96 (уже не коллапс, разумный уровень
для эмбеддингов, зажатых в узкий `epsilon`-шар вокруг похожих `e0`).

`evaluate_transfer.py` пишет `results/exp2_table.md` /
`exp2_metrics.json` — там же сравнение `entroguard_transformer
(zero-shot)` против `entroguard_lstm (adaptive)`: если zero-shot
заметно хуже adaptive по приватности — это ожидаемо и говорит о том,
что сигнал энтропии (eq. 8) частично специфичен для архитектуры, на
которой считался logit-lens; если разница небольшая — метод неплохо
обобщается за пределы семейства transformer.

Результаты (`results/*.json`, `*.md`, `*.png`) не закоммичены — они
генерируются локально командой выше и не переносимы между запусками
без переобучения (см. `.gitignore`).
